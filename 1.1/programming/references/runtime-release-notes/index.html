    Runtime release notes¶

    What changed in each release of the runtime, the control box software: new commands and fields, changed behaviour, fixed bugs, removed features, and any change to a protocol, a configuration file or the supported drive firmware range. Generated from the runtime repository's changelog at every release; which versions of the other parts a release works with is in Versions & compatibility.

    1.1.1 (2026-10-25)¶

    Fixed¶

    • Switching the read-first tick order at runtime (set_can_read_first()) no longer opens or closes a socket inside the control loop, where it could stall the loop like the loop-delay measurement did: the socket is opened once when the robot software starts. If it could not open then, the switch is refused (RTI_REFUSED).
    • rti_claim() and rti_release() refused with no PC paired said "sub_state is 'None'"; they now say the session is not paired (rti_connect() first).

    1.1.0 (2026-10-25)¶

    Added¶

    • RTI_REFUSED (6026): the real-time controller refused a command; the message gives its reason.

    Changed¶

    • Every command the robot passes to its real-time controller (58 of them: enable, home, the mode changes, stop, the jog, gripper and real-time settings, hall_check, free_joint, joint_test, set_payload, set_recipe, the reloads, ...) now replies with the controller's own answer. A refusal raises CommandRejected with its code and reason (MODE_REJECTED, ENABLE_REJECTED, HALL_CHECK_REFUSED, FREE_JOINT_REFUSED, JOINT_TEST_REFUSED, RTI_REFUSED); until now the reply was "ok" and the refusal reached only the activity log. No answer within 1 s raises RTI_NOT_RUNNING. These replies take about one control tick longer (4 to 8 ms). Asking for the mode the robot is already in is still answered "ok".

    • The test recordings in temp_data (what the measurement scripts in api_tests save) are kept to 500 MB together, down from 1 GB; the oldest runs are deleted first. On a Pi with a larger SD card, set utility/housekeeping.RECORDINGS_BUDGET_BYTES back to 1 GB.

    • The control loop's delay per joint is measured on request instead of live: the dashboard's RT Diagnostics card has a Measure button (3 s), and tools/loop_delay.py does the same in a terminal. A separate process records the CAN bus and reads the control loop's own timing; the control loop does nothing for it.

    Fixed¶

    • Single control-loop ticks of 8 to 44 ms that latched LOOP_CRITICAL and disabled the arm, now and then and at random: the live loop-delay measurement switched a CAN socket filter inside the control loop, and that call waits for the operating system's network lock whenever anything else holds it. A Wi-Fi reconnect was the usual trigger. The control loop makes no such call any more.

    1.0.0 (2026-10-25)¶

    Added¶

    • Full docstrings for the robot control commands (enable, disable, home, clear_errors, the mode changes, stop, pause, resume, safety_stop and its release, the flashing commands, and the control commands): what each does in every mode, every code it can be refused with, what it raises, and an example.
    • The same for every other public RobotClient method (waiting, connection and events, motion settings, jogging, I/O, the gripper, status and data, safety and dynamics, the real-time interface, diagnostics and service), and for RTIClient with its classes and GripperResult.

    Changed¶

    • Every speed share is a percent, and the command protocol is 2. set_joint_speed(), a move's speed, accel and jerk, and jog()'s speed take a percent: above 0 and at most 100 (0 to 100 for jog()), so 1 means 1 % and 0.5 half a percent. A value of 1 or less used to be a fraction, so a program asking for "1 %" ran at 100 %; jog()'s speed was always a fraction. A program that passes fractions must pass percents now. A client and a robot of different command protocols refuse each other at connect instead of misreading a speed.
    • When the client holding control disconnects, or loses its connection, while moves it queued still run, the robot stops the arm as stop() does. They used to play to the end with nobody connected. Call wait_idle() before disconnecting to let them finish.
    • A homing that Stop, Disable or another mode interrupts leaves the arm not homed: home it again. The arm used to stay marked homed while the joints that had started homing still read as homing.
    • Every rti_connect() switches the rate limiter, the start-pose check and real-time gravity compensation on, and sets the tool speed cap back to its start value. A session used to inherit them switched off from an earlier one, from any PC.
    • A collision-detection change returns to its start value when the client that made it releases control, loses it or disconnects. It used to last until the robot software restarted. "warn" and "stop" are refused when nothing can be checked, and the status reports "off" while the safety monitor is off.
    • set_gravity_comp() is refused while a joint moves or a PC drives the arm in a real-time session: the switch is a step in the joints' torque.
    • rti_connect() is refused outside IDLE mode and the real-time mode it asks for, and while a PC drives the arm; it used to end a running claim without braking. rti_disconnect() is refused outside IDLE mode, the real-time modes and the error state; it used to end a safety stop or a firmware flash and abandon a homing.
    • The real-time interface's settings, set_gripper(), set_joint_speed() and set_blending() refuse a value outside their range with BAD_ARGS. A negative or NaN tool speed cap used to switch the cap off, and a set_gripper() current of -1 reached the drive as 65535 mA.
    • Gripper commands are refused on a robot without a CAN gripper (NO_GRIPPER), and the queued ones while the gripper is in motor mode (GRIPPER_MOTOR_MODE). They used to be accepted and then time out or settle without moving.
    • get_joints(), get_pose() and get_digital_input() are refused with RTI_NOT_RUNNING while the control loop is not running or the robot is flashing, instead of answering old values.
    • set_log_level() refuses the loggers of the robot's other processes, which it never reached.
    • The jog's ramp settings (set_jog_accel(), set_jog_jerk_factor(), set_jog_profile()) take effect once the joint is at rest: a longer ramp applied mid-jog could carry the joint past its soft limit. set_jog_profile() and set_jog_control_mode() take any letter case, and the profile also its usual other spellings.
    • Arcs, circles and splines ignore the session's default blend (set_blending()); one that passes its own blend above 0 still fails. Every curve used to fail while a default blend was set.
    • The Hall sensor check stops by itself 2 minutes after the last hall_check(True), as a freed joint does.
    • calibrate_gripper() ends when the gripper reports itself calibrated, and drops the gripper's target: the jaws no longer move back to an old target 30 s later.
    • A gripper command's settle time grows at low speeds (about 30 s at speed 15); a slow full stroke used to fail after 5 s.
    • A first real-time command too far from the arm latches RTI_START_POSE instead of RTI_LINK_LOST.
    • The client's callbacks run on a thread of their own, so a command or a wait inside one works. on_error() receives the robot's id-less errors, on_motion_error() the failures of a lost connection, and a failure a call already raised is not raised again by wait_idle(). Waits raise RobotConnectionError for a lost connection. connect() refuses a second connect and a connection that never answered as a robot, and starts afresh. A joint number must be a whole number.
    • The telemetry recipe returns to "standard" only when the control loop starts, no longer when the dashboard or another process restarts.
    • A client that disconnects while its jog runs stops that jog: the robot brakes the joint to rest. The joint used to run on until its joint limit.
    • stop(), disable() and an error stop the gripper's jaws where they are. They used to go on to their last target and press there.
    • joint_test() on a homed arm refuses a move past the joint's soft limits, and the other joints hold still during a test. They used to float in freedrive.
    • wait_error_reset() ignores the NOT_HOMED warning, which describes a state, not a fault. It never returned on an arm that was not homed.
    • set_pid_gains() refuses an Ilim or vel_lim above the joint's limit in the robot XML, a negative gain and the gripper's drive (BAD_ARGS), and refuses to run while the robot homes or the Hall sensor check, a freed joint or a joint test runs (REJECTED): each relies on the joint's current limit, which the command resets.
    • set_digital_output() takes only true or false, 1 or 0. The Python client raises ValueError for anything else and a raw client gets BAD_ARGS; the string "false" or "0" used to switch the output on.
    • rti_set_rate_limiter(), rti_set_gravity_comp() and rti_set_start_pose_check() refuse anything but true or false with BAD_ARGS. A raw client's string "true" used to switch these protections off.
    • move_gripper() refuses a position or speed outside 0 to 255 and a current outside 1 mA to the gripper XML's current limit (BAD_ARGUMENTS). The values used to wrap at 256, and a current of -1 reached the drive as 65535 mA.
    • The control box's isolated outputs start off each time the robot software starts. After a restart, an output that had been on used to switch back on by itself.
    • home(), enter_flashing_mode(), release_safety_stop() and exit_flashing_mode() are refused with REJECTED when the robot is in a mode they cannot act in: home() needs IDLE mode and an enabled robot, enter_flashing_mode() IDLE mode or the error state, release_safety_stop() the motors off, and exit_flashing_mode() flashing mode. Before, the robot accepted the call and then refused the mode change in its activity log only, so a wait timed out. In EXEC mode, home() and enter_flashing_mode() also cancelled every client's program while the arm went on playing the moves the robot already held, and the two releases acted as enter_idle_mode() in every other mode.
    • take_control() and set_force_confirm() accept only true or false, 1 or 0, or "1" or "0" from a raw client, and refuse anything else with BAD_ARGS. The JSON string "false" used to read as true, which for take_control() meant a forced takeover. The Python client always sent a real boolean.
    • With the takeover confirmation on, the client that holds control no longer needs the button press for its own take_control(force=True).
    • A command refused for the robot's mode names the way out of that mode: clear_errors() in the error state, release_safety_stop() with the motors off, exit_flashing_mode() while flashing, and waiting while homing.

    Fixed¶

    • safety_stop() now stops the gripper's jaws where they are, as stop(), disable() and an error do.
    • A raw client's argument the robot could not read dropped that client's connection, and with it control. It is answered BAD_ARGS now, a fault on the robot's side INTERNAL.
    • A gripper command that settled on its position could report code 0, "still moving", so wait_released_part() failed an open that arrived. It reports 3.
    • rti_set_servo_generator() stored a gain before it refused a bad look-ahead; the gain then took effect later.
    • set_pid_gains() is recorded with its values in the activity log, and joint_test() checks the current limit in force after it.
    • reload_recipes() without a recipe folder answered "ok"; it answers RECIPE_DIR.
    • A network that fails silently is noticed in about 11 s on both sides (TCP keepalive); it took minutes, or never with nothing to send.
    • set_log_level("rti.handler", "DEBUG") no longer writes a line for every real-time packet from inside the control loop.
    • A jog speed that was not a number ran the joint at full speed, and a jog of a joint that does not exist was answered "ok" and raised an exception inside the control loop. Both are refused with BAD_ARGS.
    • move_gripper(position, current=...) without a speed sent the current as the speed.
    • A dry run of a gripper command moved the jaws. It now checks the command and sends nothing, as for moves.
    • In soft real-time mode the robot refused the client's stop, so RTIClient.stop() and MotionFinished ended the session with RTI_LINK_LOST. They now end it with a clean stop.
    • A callback (on_status_change(), on_motion_complete(), on_motion_error(), on_error()) that raised stopped the client's receiver: the client counted as disconnected and refused every command, stop() included. The exception is now printed and the client goes on.
    • reload_zones() with a malformed config/system.xml or gripper XML, and is_reachable() with geometry files that no longer load, dropped the client's connection. They answer ZONE_CONFIG and SELF_COLLISION_MODEL.
    • save_joint_walls() writes the robot XML through a temporary file, so a write that fails, for example on a full SD card, leaves the file as it was instead of cut short.
    • safety_stop() with an error latched switched the motors off for one control tick (4 ms) only: the robot went straight back to holding the arm. The motors now stay off until release_safety_stop(), and an error that latches while they are off no longer switches them on again.
    • After almost every restart, one control tick of about 70 ms, a few seconds after homing, latched LOOP_CRITICAL and disabled the robot. It was Python's garbage collector walking every object the real-time process made while starting. Those objects are now frozen before the control loop starts: on the arm, a full collection took 67 ms before and 0 ms after. Any collection that still pauses the loop for more than 5 ms is logged in RTI.log.
    • The dashboard's firmware-flashing override dialog said the motors lose torque within about 5 s. It now shows the drive watchdog time from config/system.xml, 0.1 s, and says that the joints brake and the gripper coasts.

    Removed¶

    • RobotClient.rti_set_profile(). It sent a command the robot no longer has, so every call failed with UNKNOWN_CMD. Choose the streaming contract with rti_connect(pc_ip, rate_hz=...): with a rate the robot uses the soft real-time mode, without one the hard real-time mode.

    0.10.0 (2026-10-23)¶

    Added¶

    • VERSIONING.md: which version to change for which kind of change, and how a release is made, including the documentation.
    • docstrings_guide.md: how every docstring is written. The documentation's Python API reference is built from the robotclient docstrings.
    • Full docstrings for the motion commands (move_joints, move_pose, move_linear, the arc, circle and spline moves and their relative forms, delay): every argument with its unit, every per-move setting, what the call returns and raises, every error code it can fail with once the robot accepted it, and an example.

    Changed¶

    • Every command has one documented name. Its old names keep working, in Python (the same function) and on the wire (the robot maps an old command ID to its command):
    • The relative moves are move_linear_rel_world / move_linear_rel_tool, and the same for arcs, circles and splines. _rel_wrf / _rel_trf are their other names.
    • The gripper commands start with the verb, as every other command does: open_gripper, close_gripper, calibrate_gripper. gripper_open, gripper_close and gripper_calibrate still work.
    • set_profile and set_ik_solver are the names of their pairs; set_default_profile and set_default_ik_solver still work. latest_status() is the new name of status(), so that it is not mistaken for get_status(), which asks the robot.
    • A command's wire ID is its method's name. Fourteen settings were sent under another ID, for example gravity_comp for set_gravity_comp and jog_set for jog. The robot accepts both IDs. A client from this release reads the robot's version when it connects and sends an older robot the IDs it knows, so a program runs on either; only a command that did not exist on the older robot is refused there, as before.
    • delay() refuses a time of 0 or less, or one that is not a finite number, with INVALID_DURATION, the moves' rule for duration. It used to finish after about 8 ms without an error, so delay(-5) written for delay(5) went unnoticed. A G-code G4 P0 dwell still pauses for nothing (the G-code runner skips it), and a negative P is refused when the program is read.

    Fixed¶

    • move_joints(..., dry_run=True) and delay(..., dry_run=True) planned the move and sent it to the robot, so a "dry" joint move moved the arm. They now plan and check it and send nothing, as every other move already did. Two more ways a dry run reached the robot are closed: a dry-run move with a zone, tolerance or ruckig_corner blend was planned and sent as part of the blended chain around it (any move type), and a move blended toward a dry-run successor was sent carrying a corner speed into a move that never came. A dry run now never joins a chain, and the move before it ends at rest.
    • A dry run of move_pose, move_linear, the relative moves and the arc, circle and spline moves stopped after the inverse kinematics, before the timing and the joint-limit, safety-zone and self-collision checks, so it could pass a move the robot then refused. Every move's dry run now plans in full and runs every check, then sends nothing.
    • With profile="toppra", a timing failure on a straight-line or curved move was reported as PLAN_FAIL. It is now TOPPRA_INFEASIBLE or TOPPRA_UNAVAILABLE, as on joint moves.
    • move_pose now has the acceleration check every other move has: a planned motion over the acceleration limit is refused with ACCEL_LIMIT_VIOLATION instead of being sent.
    • The motion docstrings listed completion_policy as a per-move setting, which the robot refuses: it is a session setting, changed with set_completion_policy(). They now name all 13 per-move settings the robot accepts.

    0.9.0 (2026-10-22)¶

    The first numbered release. The runtime had no version before this one, so this section describes what 0.9.0 contains, then the changes that affect programs written for the earlier, unnumbered code.

    Contents¶

    • Real-time control loop at 250 Hz on a core of its own, with real-time scheduling and locked memory. The CAN interrupt work has a core of its own too. The loop reads the drives first and sends their commands early in each tick.
    • Queued motion (EXEC): joint, linear, relative and pose moves, with five motion profiles. The default profile is jerk-limited. Moves can be blended, and a G-code subset is supported. Pause, resume and stop all brake along the planned path. Every move is checked against the joint limits, the safety zones and self-collision before it starts. A failed move aborts the program.
    • Real-time streaming: a hard real-time mode, where a PC sends one target every tick, and a soft mode, where the robot interpolates targets sent at a lower rate. Both stop under control and refuse motion the arm cannot do.
    • Safety:
    • a safety monitor for joint limits, endstops, overspeed, tracking, a buzzing hold, and contact or collision
    • safety zones, with walls you can feel in freedrive
    • freedrive walls at every joint limit
    • self-collision checks in the planner, the monitor and jogging
    • a 100 ms drive watchdog
    • an E-stop channel policy per control box PCB version
    • Dynamics: gravity compensation, inertia and Coriolis feedforward, a declared payload, and an external torque estimate that stays valid while the arm moves.
    • Homing that recognises the arm and reports each failure with its reason.
    • Tools around the robot:
    • the web dashboard on port 8081
    • block programming
    • drive firmware updates over CAN
    • a guided first-run check of a newly built robot
    • an activity log, incident recordings and a support bundle
    • a simulated robot for testing without hardware
    • Versioning:
    • robot.get_versions() reports every part's version
    • configuration files carry a format number
    • the three protocols carry a version number each, and the Python client checks them when it connects
    • the robot and gripper XMLs name their hardware revision
    • the runtime declares the drive firmware it supports

    Changed: affects programs written for the earlier code¶

    • Pose angles. A pose [x, y, z, rx, ry, rz] now means R = Rx(rx) Ry(ry) Rz(rz): about the base X axis by rx, then the tool's new Y axis by ry, then its own Z axis by rz. Stored poses, recordings and logs from before keep the old angles. Saved block programs in the old format convert when they are read. The Python client takes pose angles in radians by default, or in degrees with angle_unit="deg".
    • Pose commands need a declared protocol. The executor refuses a command that carries pose angles with CLIENT_TOO_OLD when the client declares no command protocol version, because a client from before 0.9.0 means the old angles. The Python client declares it. A client that sends raw JSON adds "protocol": 1 to each message.
    • Per-joint error keys count from 1. J1:... is the first joint.
    • Hard real-time streaming needs the send time on every position target, and runs over UDP only. The Python client sends it by default.
    • The default EXEC motion profile is jerk-limited. A joint move with no profile takes about 1.5 times as long as with the old trapezoid, while a straight TCP line was measured slightly faster. Pass profile="trapezoid" for the old timing.
    • A stop in EXEC holds the arm in EXEC instead of switching to freedrive.
    • The drive watchdog is 100 ms. It was 5 s. The arm is no longer held about 0.1 s after the runtime stops.
    • Log lines have one format: LEVEL | UTC time | tick | logger | message. Scripts that parse the logs should use utility/logger_setup.parse_line.

    Known limitations¶

    • This runtime is not a safety-rated system. The E-stop is the safety function.
    • The control box board does not report its own version yet. The PCB version is declared in config/system.xml.
